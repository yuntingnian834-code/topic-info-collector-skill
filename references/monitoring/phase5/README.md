# 第五阶段：数据新鲜度与发布可靠性

第五阶段解决“采集任务已经成功，但网页仍显示旧日期”的交付断层。核心目标是让网页始终明确展示数据日期、数据来源和新鲜度，并在实时读取失败时回退到最近一次成功快照，而不是展示过期演示日期。

## 已完成能力

### 页面日期可信

- 首页、情报库和每日简报移除写死的 `2026-08-06`，数据返回前统一显示“正在读取最新数据”。
- 页面根据接口 `sampleDate` 和 `meta.freshness` 展示“当日数据已同步 / 最近成功快照 / 实时数据暂不可用”。
- 即使当天0条记录，也会更新日期、数量和空状态，不再停留在演示数据。

### D1每日快照

- 新增 `site_snapshots`，按自然日保存成功返回的完整网页数据、记录数、生成时间和刷新时间。
- 当日已有有效快照时直接返回D1数据，避免每次访问都遍历飞书历史记录。
- 当日实时读取失败时回退最近一次成功快照，并明确标记为 `stale`；没有任何快照时标记为 `unavailable`。
- 空快照10分钟后允许重新读取；强制刷新1分钟内自动限流；只保留最近35天快照。

### 自动预热与一致性校验

- 每日采集完成后调用公开数据接口进行缓存预热，并将网页日期、网页记录数与 `pipeline-result.json` 对齐。
- 新增独立新鲜度任务，每天北京时间08:00、12:00检查并刷新数据。
- 生成 `latest_freshness.json` 和 `latest_freshness.md`，异常时通过独立监控机器人发送飞书卡片。

## 初始告警规则

| 规则 | 等级 | 条件 |
|---|---|---|
| 数据接口不可用 | P0 | 实时数据和历史成功快照都不可用 |
| 多端数量不一致 | P0 | 任务记录数不等于网站记录数 |
| 日期落后两天及以上 | P0 | `lag_days >= 2` |
| 日期落后一天 | P1 | 网站日期不等于北京时间当天 |
| 当日数据为空 | P1 | 08:00后网站仍为0条且没有任务侧期望值 |

## 使用方式

```bash
# 只检查线上日期和记录数
python scripts/monitoring/phase5/freshness_monitor.py \
  --site-url https://shu-signal-intelligence.yuntingnian834.chatgpt.site

# 强制刷新，并与当日任务结果核对
python scripts/monitoring/phase5/freshness_monitor.py \
  --site-url https://shu-signal-intelligence.yuntingnian834.chatgpt.site \
  --refresh \
  --pipeline-result pipeline-result.json
```

## 完成标准

1. 页面源码不包含固定业务日期。
2. 当日快照命中时无需重新遍历飞书历史记录。
3. 实时读取失败时仍能返回最近一次成功数据，并标记为过期。
4. 网页日期、网页记录数与每日任务结果可自动核对。
5. 异常检查不会阻塞采集、飞书入库和简报推送。

## 面试表达

> 项目上线后我发现，采集成功不等于用户一定看到最新数据。于是第五阶段补充了交付新鲜度治理：网页不再写死日期，而是展示真实快照日期和新鲜度；成功数据按天缓存到D1，正常访问直接读取缓存，飞书异常时回退最近成功快照；每日任务结束后再自动核对网站日期和记录数，并按P0/P1告警。这样把监控从“系统有没有运行”推进到了“用户最终看到的数据是否正确且及时”。
