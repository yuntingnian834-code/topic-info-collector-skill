# 第四阶段：异常告警与持续维护

第四阶段把前三阶段的运行、模型和用户行为数据转化为可执行的治理闭环：看板发现问题，规则生成告警，用户负反馈和零结果搜索自动进入Bad Case，维护者处理后更新状态，Prompt调整再通过固定评测集回归。

## 已完成能力

### 用户价值看板

- 新增 `monitoring-dashboard.html`，支持最近7天/30天切换。
- 展示每周有效情报、有用率、列表到详情、详情到原文、搜索使用和零结果率。
- 展示访问转化链路、每日行为趋势、渠道表现和无用原因分布。
- 按最小样本量计算P1/P2告警，避免少量数据造成误报。

### Bad Case回流

- “暂时没用”反馈按情报聚合；反馈恢复为有用时自动关闭案例，再次出现时自动重开。
- 零结果搜索按脱敏关键词聚合；重复事件ID不会重复累计。
- D1 `quality_reviews` 保存来源、类型、出现次数、处理状态和时间。
- 公开看板隐藏零结果原词；输入 `MONITORING_ADMIN_KEY` 后可查看并将状态切换为待处理、处理中或已解决。密钥只保存在页面内存。

### Skill运行告警与人工抽检

- 后台报告新增10条初始规则，覆盖运行失败、全部来源失败、多端不一致、有候选但0写入、来源失败比例、候选量偏离7日基线、模型成功率、JSON一次成功率和降级率。
- 告警分为P0/P1并写入本地 `runtime_alerts`；飞书每日运行卡片同步展示异常和建议动作。
- 每周一从最终保留和系统拦截文章中各抽最多5条，写入本地 `quality_reviews`，重复生成不增加重复记录。
- 抽检字段覆盖相关性、事件日期、指标、摘要忠实度、Bad Case类型、修复和回归状态。

### 自动周报与保留策略

- `user_value_monitor.py` 每天读取网站汇总：工作日仅有异常时通知，周一固定发送7天周报。
- 每月1日自动生成30天治理复盘；也可通过GitHub Actions手动选择7天/30天和通知方式。
- 网页行为默认保留180天，已解决Bad Case保留365天；维护接口默认只预检可删除数量，只有显式 `apply=true` 才执行。
- Skill本地监控同样提供180/365天删除预览，不会自动删除历史数据。

## 初始告警阈值

| 规则 | 等级 | 判断条件 |
|---|---|---|
| Skill运行失败 | P0 | `status=failed` |
| 全来源失败 | P0 | 来源总数>0且成功数=0 |
| 多端不一致 | P0 | 飞书/网页或汇总/明细不一致 |
| 有候选但0写入 | P1 | candidate>0且written=0 |
| 来源失败偏高 | P1 | 来源≥3且失败比例≥30% |
| 候选量异常 | P1 | 至少3次基线后低于50%或高于200% |
| 模型成功率偏低 | P1 | 调用≥5且成功率<90% |
| JSON一次成功率偏低 | P1 | 调用≥5且成功率<85% |
| 降级率偏高 | P1 | 调用≥5且降级率>20% |
| 搜索零结果偏高 | P1 | 搜索≥5且零结果率≥30% |
| 情报有用率偏低 | P1 | 反馈≥5且有用率<50% |
| 正式访问缺失 | P2 | 观察窗口内production访问会话=0 |
| 原文转化偏低 | P2 | 详情会话≥10且原文点击率<20% |
| Bad Case积压 | P2 | 待处理/处理中案例≥10 |

第一周应观察真实基线，第二周再根据业务波动调整阈值，不把“当天0条情报”单独视为故障。

## 使用方式

```bash
# 查看最近一次运行告警与治理状态
python scripts/monitoring/phase4/governance.py --json

# 立即建立一批保留/拦截人工抽检样本
python scripts/monitoring/phase4/governance.py --force-review-queue

# 手动生成7天用户价值报告
python scripts/monitoring/phase4/user_value_monitor.py --site-url https://你的站点地址 --days 7 --notification-mode never
```

网站正式发布前需要配置 `MONITORING_ADMIN_KEY`；自动周报使用 `SHU_SIGNAL_SITE_URL` 和已有的 `MONITORING_FEISHU_WEBHOOK_URL`。

## 面试表达

> 项目上线后，我没有只看采集量，而是把监控做成持续治理闭环。运行侧设置P0/P1规则，覆盖来源、漏斗、模型、Prompt和多端交付；用户侧用转化漏斗、有用率和零结果率判断价值。负向反馈与零结果搜索会自动进入Bad Case台账，每周同时抽检保留和拦截样本，修复后再跑固定评测集。这样可以区分系统故障、Prompt退化和产品价值不足，并用数据决定下一步优化。
