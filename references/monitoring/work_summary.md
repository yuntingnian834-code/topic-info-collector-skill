# SHU SIGNAL 数据监控建设总结

## 工作目标

在原有AI情报采集、过滤、飞书入库与网页展示基础上，补齐“过程可追踪、模型可评估、用户价值可验证、异常可治理、网页数据可保鲜”的完整监控体系。

## 五阶段成果

| 阶段 | 主要成果 | 可回答的问题 |
|---|---|---|
| 第一阶段 | 任务、来源、文章事件与完整提纯漏斗 | 130条信息在哪一环损耗，为什么最终保留48条 |
| 第二阶段 | 模型调用、Prompt版本、Token、延迟、重试、降级与固定评测集 | 质量下降来自模型、Prompt还是结构化输出 |
| 第三阶段 | 5个页面、10类行为事件、反馈与匿名渠道归因 | 用户是否查看详情、打开原文并认可情报 |
| 第四阶段 | 15条告警、Bad Case回流、双向抽检、7/30天看板与周/月报 | 问题如何被发现、归因、修复和回归 |
| 第五阶段 | 页面真实日期、D1每日快照、失败回退、08:00/12:00新鲜度检查 | 采集成功后，用户最终看到的数据是否正确及时 |

## 量化交付

- Skill侧形成任务、来源、文章、模型、抽检、告警等结构化数据。
- 网页侧形成用户事件、反馈、Bad Case和每日快照4类D1数据。
- 用户价值看板支持7天/30天窗口与完整访问漏斗。
- 告警覆盖运行、来源、模型、Prompt、用户价值、Bad Case和数据新鲜度。
- 每周最多抽检10条保留/拦截样本；行为数据保留180天，已解决Bad Case保留365天，网站快照保留35天。
- 自动任务覆盖每日采集、每日数据新鲜度检查、每周用户价值报告和每月治理复盘。

## 最终闭环

```text
采集与提纯 → 飞书/网页交付 → 运行与模型监控 → 用户行为与反馈
      ↑                                      ↓
固定评测回归 ← Prompt/规则修复 ← 告警与Bad Case ← 新鲜度核对
```

## 简历/面试概括

> 我在完成AI情报产品0到1落地后，继续搭建了五阶段数据治理体系：用run_id和article_id还原提纯漏斗，记录模型与Prompt版本、Token和降级表现，通过网页埋点和有用性反馈验证用户价值，再用分级告警、Bad Case、双向抽检和固定评测集形成优化闭环。最后补充D1每日快照与交付新鲜度校验，确保采集结果真正以正确日期和数量到达用户端。
